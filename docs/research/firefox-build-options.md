# Пересборка Firefox для B8000-H: возможности и границы

Исследовано 18 октября 2026 года. Изменение настроек, сборка, установка и испытания браузера не выполнялись. Ниже — план экспериментов, а не готовый проверенный mozconfig. Поддержка флага в исходниках не доказывает, что данная комбинация собирается на Alpine ARMv7.

## Исходные условия и надёжность

README проекта порта сообщает: Alpine 3.24 armv7, 1 ГБ RAM и 512 МБ zram; phoc использует GPU через libhybris, приложения рисуют процессором; аппаратного декодирования видео нет. Это сведения владельца порта, не измерения устройства в этой сессии. См. [README порта](https://github.com/trudenboy/lenovo-b8000h-linux/blob/95c3d33638857efc6eea67890fff4a0b3d7c9ad2/README.md).

Проверены текущие исходники aports на коммите `333bbfe1bcc7bc2a9da65c0e4f0186911401c60a` и Gecko на `c0ad8e7c1d3d33cf3405f7019994471ac8baf4e7`. Это разные точки разработки, не обещание совместимости. Версию установленного браузера нужно получить с планшета; версия языкового XPI в этом репозитории её не доказывает. Перед пересборкой нужен APKBUILD именно установленной ветки Alpine, tarball именно выбранного исправленного выпуска и соответствующий набор патчей.

## Что уже делает Alpine

В проверенном [APKBUILD Firefox](https://github.com/alpinelinux/aports/blob/333bbfe1bcc7bc2a9da65c0e4f0186911401c60a/community/firefox/APKBUILD) ARMv7 идёт по ветке regular: без PGO и без добавления LTO; комментарий связывает отказ от PGO с памятью/проблемами платформ. Используются Clang 22 и `-O2`; ARMv7 получает `--disable-profiling`. Версия файла — 154.0, это не автоматически установленная/рекомендуемая версия устройства. `LD_PRELOAD=libmimalloc-insecure` относится к процессу сборки. Добавление Scudo в исполняемый файл исключает `arm*`; из этого APKBUILD нельзя делать вывод, что Firefox на планшете работает под mimalloc или Scudo. Уверенность высокая, вывод ограничен данным коммитом.

[Alpine mozconfig](https://github.com/alpinelinux/aports/blob/333bbfe1bcc7bc2a9da65c0e4f0186911401c60a/community/firefox/mozconfig) уже выключает updater, crashreporter, tests, debug/debug-symbols, jemalloc; включает release, hardening, lld, packed-relative-relocs и системные библиотеки. Повторение этих параметров не создаёт дополнительной экономии. `--disable-strip` не означает, что конечный APK непременно содержит все символы: упаковка дистрибутива имеет отдельную обработку. Результат проверять по готовому пакету. Уверенность высокая.

[ESR APKBUILD](https://github.com/alpinelinux/aports/blob/333bbfe1bcc7bc2a9da65c0e4f0186911401c60a/community/firefox-esr/APKBUILD) также оставляет ARMv7 без PGO/LTO, отдельно выключает crashreporter на ARMv7 и некоторых других архитектурах. Его [mozconfig](https://github.com/alpinelinux/aports/blob/333bbfe1bcc7bc2a9da65c0e4f0186911401c60a/community/firefox-esr/mozconfig) близок к обычному. ESR — полезная более стабильная база сопровождения, но не доказательство меньшей RAM. Сравнивать только актуальные поддерживаемые пакеты; заморозка старого Firefox ради памяти не является оптимизацией безопасности.

## 32-битная поддержка: важное различие

[Объявление Mozilla](https://blog.mozilla.org/futurereleases/2025/09/05/firefox-32-bit-linux-support-to-end-in-2026/) прекращает официальные **x86** 32-bit Linux builds после 144; оно уточнено именно для x86. Это не объявление о запрете ARMv7 в исходниках и не готовый ARMv7 musl-бинарник. [Mozilla Support](https://support.mozilla.org/en-US/kb/firefox-has-ended-support-32-bit-linux) отдельно допускает, что дистрибутивы продолжают поставлять собственные сборки с другими требованиями. Работоспособность ARMv7 здесь обеспечивается downstream Alpine/сообществом и требует проверки.

Снимок Alpine `firefox-esr` с 140.14.0 в этом отчёте — свидетельство устройства сборки, **не рекомендация устанавливать эту версию**. В [объявлении release manager Mozilla от 15 сентября 2026](https://groups.google.com/a/mozilla.org/g/announce/c/V5pu9KAc9H0) ESR153 назван заменой ESR140 с 13 октября 2026. На дату исследования нельзя предлагать ESR140 как долгосрочную поддерживаемую базу без отдельной проверки актуальных security releases и downstream-backports. Наличие APKBUILD в git само по себе не удостоверяет безопасность/актуальность опубликованного APK.

## Наиболее полезные сборочные эксперименты

### 1. ThinLTO до PGO

В Gecko существует `--enable-lto` с режимами `thin`, `full`, `cross`. `cross` здесь означает оптимизацию между C++ и Rust, а не кросс-компиляцию на другую архитектуру. С Clang обычный выбор вне специальных x86_64 automation/PGO условий — ThinLTO. При profile-generate LTO отключается. Cross-language LTO с GCC отклоняется. Есть ограничение импортируемых инструкций для сдерживания роста кода. См. [lto-pgo.configure](https://github.com/mozilla-firefox/firefox/blob/c0ad8e7c1d3d33cf3405f7019994471ac8baf4e7/build/moz.configure/lto-pgo.configure).

Предложение: на мощном сборочном хосте сначала получить точную воспроизводимую копию Alpine APK, затем отдельный вариант с `--enable-lto=thin`. После его проверки — `--enable-lto=thin,cross` при совместимых LLVM Clang/Rust и наборе патчей aports. Различие в строках mozconfig не гарантирует применение: смотреть configure output и фактические команды линковки. Full LTO оставить последним из-за расходов сборки; доказательств его преимущества на Cortex-A7 нет. Возможный выигрыш — код/локальность/CPU, снижение heap не обещается. Уверенность в существовании режимов высокая, в выигрыше на данном устройстве низкая до измерений.

### 2. PGO с реальным ARM-профилем

[Официальный интерфейс PGO](https://firefox-source-docs.mozilla.org/build/buildsystem/pgo.html) — `MOZ_PGO=1`; по умолчанию используется profileserver. Для разделённых стадий существуют profile-generate/profile-use, путь к merged.profdata и jarlog; aports уже показывает такой конвейер для других архитектур. Производство PGO-профиля требует запуска instrumented целевого браузера: быстрый x86_64 хост не превращает x86_64 запуск в профиль ARMv7. Можно собирать на хосте, профилировать на планшете и вернуть данные на хост; это отдельная инженерная проверка, не проверенная здесь готовая команда.

Профиль должен включать запуск, прокрутку и набор текста, типовые сайты, блокировщик, фото и аудио; не обучать только одному Speedometer. Реальное устройство даёт более представительный профиль, чем пользовательский QEMU с другим графическим стеком. Проверить, помещается ли instrumented Firefox в память и не убивается ли earlyoom. Слишком тяжёлое профилирование на планшете может заблокировать этот путь даже при достаточной RAM сборочного хоста.

[Mozilla benchmarking](https://firefox-source-docs.mozilla.org/performance/Benchmarking.html) сообщает потенциальное улучшение runtime от PGO, но это не обещание процента ARMv7 или экономии RAM. Debug и неoptimised сборки для сравнения производительности непригодны. Rust должен быть release-оптимизирован; случайная локальная developer-сборка может быть медленнее пакетной.

### 3. Размер кода против CPU

[Clang](https://clang.llvm.org/docs/CommandGuide/clang.html) определяет `-O2` как основной оптимизированный уровень, `-O3` допускает больший код ради скорости, `-Os`/`-Oz` ориентированы на размер. Из меньшего libxul не следует пропорциональное уменьшение RAM: нужны resident исполняемые страницы, private dirty и heap по отдельности. Проверять варианты `-O2`, `-Os`, затем при наличии смысла `-Oz` и `-O3`, сохраняя hardening. `-Ofast` и fast-math не включать: они меняют гарантии вычислений. Ни один уровень нельзя объявить лучшим без измерений.

[Документация mozconfig](https://firefox-source-docs.mozilla.org/setup/configuring_build_options.html) предупреждает, что дополнительные опции снижают вероятность корректной сборки, и рекомендует минимальные изменения. Доступные параметры выбранной версии проверять через `mach configure -- --help`. `--disable-tests` экономит сборочное время/диск; сам по себе не доказывает экономию работающего браузера. Сохранять `--enable-release` и проверять фактическую оптимизацию Rust.

[Rust codegen options](https://doc.rust-lang.org/rustc/codegen-options/index.html) отдельно управляют opt-level и target-cpu; CPU задаётся для целевой архитектуры, `native` означает CPU хоста. Размерные `s`/`z` не гарантируют монотонного уменьшения бинарника. Не задавать глобальные CARGO_PROFILE_RELEASE_* поверх механизмов Gecko вслепую: Alpine специально снимает эти переменные. Сперва оставить Rust как в Alpine; отдельный size-вариант допустим после проверки `RUSTC_OPT_LEVEL` и поддерживаемых значений в исходниках выбранного выпуска.

### 4. Cortex-A7, ARM/Thumb и NEON

[arm.configure](https://github.com/mozilla-firefox/firefox/blob/c0ad8e7c1d3d33cf3405f7019994471ac8baf4e7/build/moz.configure/arm.configure) подтверждает `--with-arch`, `--with-thumb`, `--with-fpu`, `--with-float-abi`; для Linux исходные значения берутся из toolchain. Поэтому список Android ARM-настроек нельзя копировать в Alpine. Firefox уже умеет строить отдельные NEON-пути; глобальный `-mfpu=neon` не открывает прежде отсутствующее ускорение автоматически.

Эксперимент после чтения `/proc/cpuinfo` и ELF attributes: C/C++ `-mcpu=cortex-a7`, затем Thumb-2 против ARM; Rust `-C target-cpu=cortex-a7` только после проверки списка CPU целевого rustc и путей применения aports. ABI должен остаться совместим с armv7 musl hard-float. Никогда не применять `-march=native` на x86_64 машине для ARM-сборки. Системные библиотеки, JIT-код и заранее собранные зависимости не становятся Cortex-A7-специализированными только из-за CFLAGS libxul. Уверенность в механизмах высокая, в чистом выигрыше низкая.

### 5. Аллокатор

[Gecko memory.configure](https://github.com/mozilla-firefox/firefox/blob/c0ad8e7c1d3d33cf3405f7019994471ac8baf4e7/build/moz.configure/memory.configure) поддерживает `--enable-jemalloc`, по умолчанию включая его на Linux; Alpine намеренно отличается. Значит, mozjemalloc — осмысленный отдельный A/B-кандидат, а не рекомендация немедленно менять libc/LD_PRELOAD. Измерять рост памяти за 1–3 часа, возврат после закрытия вкладок и latency, а не только старт. Сначала проверить текущие musl-патчи, совместимость и полный запуск. Уменьшение fragmentation зависит от нагрузки; проценты не известны. Переход на glibc ради allocator-предположений меняет слишком много факторов и усложняет Alpine-порт.

## Что можно удалить и какой ценой

Проверенный [toolkit/moz.configure](https://github.com/mozilla-firefox/firefox/blob/c0ad8e7c1d3d33cf3405f7019994471ac8baf4e7/toolkit/moz.configure) содержит `--disable-webrtc`, `--disable-accessibility`, `--disable-webspeech`, `--disable-webdriver`. Это кандидаты после проверки потребностей: звонки/захват; экранный диктор/AT-SPI; речь; автоматизация соответственно. Потерю доступности и автотестов учитывать явно. `MOZ_TELEMETRY_REPORTING` управляет reporting, не доказывает удаление всех счётчиков/Glean. Для AV1 подтверждён системный backend, универсальный актуальный `--disable-av1` здесь не подтверждён. Не выдавать старые `--disable-wave`, `--disable-ffmpeg`, `--disable-webm` за проверенные рецепты. Невыполняемые кодеки главным образом влияют на размер, а не обязательно на idle CPU/RAM.

`MOZ_DEVTOOLS` допускает только `all`/`server`, а [browser/moz.configure](https://github.com/mozilla-firefox/firefox/blob/c0ad8e7c1d3d33cf3405f7019994471ac8baf4e7/browser/moz.configure) включает `all`. Простого подтверждённого современного `--disable-devtools`/`MOZ_DEVTOOLS=none` не найдено. Полное вырезание — сопровождение патча, потенциальные зависимости frontend и потеря диагностики. Не ставить это перед LTO/PGO.

[JS configure](https://github.com/mozilla-firefox/firefox/blob/c0ad8e7c1d3d33cf3405f7019994471ac8baf4e7/js/moz.configure) поддерживает `--disable-jit`; старый `--disable-ion` помечен deprecated с ошибкой. Отказ от JIT может уменьшить кодовую память, но несёт риск резкого роста CPU и задержек JS и потери возможностей WebAssembly. Это только отдельный kiosk-профиль для заранее известного набора простых страниц; для общего браузера оставить JIT. Наличие опции не доказывает корректную сборку всего desktop Firefox без JIT.

## Сопровождение и критерии решения

Linux ARMv7 относится к менее защищённым CI платформам Mozilla: [supported configurations](https://firefox-source-docs.mozilla.org/build/buildsystem/supported-configurations.html) перечисляет desktop Linux x86_64/AArch64 как Tier-1, прочие ARM Linux как Tier-3. Поэтому основа — Alpine patches, не чистый upstream tarball. Официальные [требования сборки Linux](https://firefox-source-docs.mozilla.org/setup/linux_build.html) — минимум 4 ГБ, рекомендуется 8+ и 30 ГБ диска; для LTO/PGO разумный проектный резерв — 16–32 ГБ и 60–100 ГБ SSD, это практическая оценка, не требование Mozilla и не измеренный пик. Собрать на планшете 1 ГБ — непрактичная исходная стратегия. Кросс-сборка требует ARM musl sysroot и сборочных host tools, поддержка конкретной комбинации проверяется отдельно.

Предлагаемая очередь: штатный APK → точная пересборка без изменений → ThinLTO → PGO → сравнение -Os/O2 → CPU tuning → allocator → узкое удаление функций. Не запускать полный декартов перебор. Если первые варианты не дают результата, остановить ветку раньше расходов на поддержание форка.

Протокол принятия (предложенные пороги, не результаты): один source revision, один OS snapshot, одинаковые профили/блокировщик, 5 чередующихся прогонов после охлаждения; отдельно cold/warm start. Суммировать PSS дерева Firefox и swap, private dirty, major faults, CPU time, задержку ввода/прокрутки, время загрузки, OOM/earlyoom, расход батареи при фиксированной яркости. Отдельно libxul ELF text/disk. По возможности добавить memory reports до/после закрытия вкладок. Проверки: пустой браузер, типичная одна страница, три вкладки, тяжёлая SPA, фото, аудио, доступное software video, час повторных переходов. Ни sum RSS, ни один Speedometer не достаточны.

Принять вариант при воспроизводимой экономии ≥10% PSS/swap или ≥15% CPU времени/latency, без >10% ухудшения других ключевых сценариев и без новых сбоев. Для небольшого улучшения принять только почти бесплатную в сопровождении конфигурацию. Сохранить sandbox, изоляцию, TLS, hardening и обновляемость. Каждый выпуск должен пересобираться после security-update с автоматическим smoke/совместимостью; иначе пакетная версия предпочтительнее. Реальную экономию MB/% до опытов обещать нельзя.
